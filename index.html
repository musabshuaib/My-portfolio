I got into this work because most "AI features" quietly fall apart the moment a real user does something unexpected — I like the part where you make them not do that.

My background is backend engineering, which shows up in how I treat agents: as distributed systems with an unreliable component (the model) at the center, not as magic. That means structured evals before launch, fallbacks and confirmation steps for anything irreversible, and logging good enough to debug a bad decision after the fact.

Outside of agent orchestration, I spend a lot of time on retrieval quality — the unglamorous work of chunking, re-ranking, and eval sets that actually correlates with what users complain about.

How I build agents

Irreversible actions get a checkpoint.

If an agent can refund money or send an email, it confirms or logs before it acts — the model's confidence is not the same as being right.

If it isn't evaluated, it isn't shipped.

Every agent gets a hold-out set of real cases before launch, and the same set gets re-run on every prompt or model change.

Traces are a debugging tool, not a log dump.

I log thought → call → observation as structured steps so a bad answer can be replayed and understood, not just flagged.
